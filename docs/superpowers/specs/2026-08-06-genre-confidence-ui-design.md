# 장르 예측 앱 상대적 신뢰도 UI 설계

## 목표

데이터와 지원 장르가 제한된 현재 RandomForest 모델을 재학습하지 않고, 예측 결과의 불확실성과 학습 범위를 사용자가 한눈에 이해하도록 `app.py`의 결과 화면을 개선한다.

## 성공 조건

- 기존 모델·LabelEncoder·StandardScaler·57개 feature pipeline은 변경하지 않는다.
- 사용자가 수정한 앱 제목, caption, 모델 설명 문구를 보존한다.
- 기존 sidebar의 지원 장르 10종을 유지한다.
- Top-1 확률뿐 아니라 Top-1과 Top-2의 차이(margin)를 함께 표시한다.
- 결과를 `높음`, `보통`, `낮음`의 상대적 신뢰도 단계로 표시한다.
- 낮은 신뢰도 결과를 확정된 장르처럼 설명하지 않는다.
- 신뢰도 단계가 확률 calibration 결과가 아니라 UI 설명용 heuristic임을 코드와 문서에 명시한다.
- 업로드·예측·시각화 실패 시 임시 WAV가 남지 않도록 정리한다.

## 변경하지 않는 범위

- RandomForest 재학습
- 학습 데이터 추가 또는 교체
- 장르 종류 확장
- feature 추출 방식과 순서
- 모델 확률 calibration 또는 정식 OOD 탐지
- 멀티파일 업로드와 예측 이력

## 상대적 신뢰도 규칙

Top-3 결과에서 다음 값을 사용한다.

```text
top1_probability = 1위 확률
margin = round(1위 확률 - 2위 확률, 4)
```

`margin`은 부동소수점 경계 비교가 실행 환경에 따라 흔들리지 않도록 소수점 넷째 자리에서 고정한다.

판단 규칙은 다음과 같다.

| 단계 | 조건 | 화면 의미 |
|---|---|---|
| 높음 | `top1 >= 0.50` 그리고 `margin >= 0.15` | 현재 10개 장르 안에서 상대적으로 뚜렷한 결과 |
| 보통 | `top1 >= 0.30` 그리고 `margin >= 0.08` | 후보가 있으나 결과 해석에 주의 필요 |
| 낮음 | 나머지 | 장르를 확정하기 어려움 |

이 기준은 validation set으로 보정된 확률 기준이 아니다. 모델 결과를 사용자가 해석하도록 돕는 heuristic이며, README와 코드 주석에서 이를 명시한다.

## UI 구조

### 상단

- 기존 제목 `🎵 음악 장르 예측기` 유지
- 기존 사용자 caption 유지
- WAV uploader와 audio player 유지

### Sidebar

- 지원 장르 10종 유지
- RandomForest·57 feature 설명 유지
- `이 모델은 위 10개 장르만 구분합니다.` 안내 추가

### 결과 영역

왼쪽 결과 카드와 오른쪽 멜스펙트로그램의 2열 구조를 유지한다.

왼쪽 결과 카드:

- Top-1 장르
- `높은/보통/낮은 신뢰도` badge
- Top-3 확률 막대
- Top-1 확률과 margin 근거
- 단계별 해석 문구

오른쪽 시각화 카드:

- 기존 멜스펙트로그램
- `학습 범위 밖의 곡은 가장 가까운 기존 장르로 분류될 수 있습니다.` 안내

### 단계별 문구 원칙

- 높음: `현재 지원 장르 안에서 비교적 뚜렷한 결과입니다.`
- 보통: `가능성은 있지만 다른 후보와 함께 확인해야 합니다.`
- 낮음: `결과를 확정하기 어렵습니다.`

`정확히 맞혔다`, `신뢰할 수 있다`, `실제 장르다` 같은 과장 표현은 사용하지 않는다.

## 코드 구조

신뢰도 판단을 Streamlit UI 코드와 분리된 순수 함수로 만든다.

```python
def assess_confidence(top3):
    """Top-3 예측으로 상대적 신뢰도 단계와 근거를 반환한다."""
```

반환값에는 다음 정보가 포함된다.

```text
level       높음/보통/낮음
top1_prob   1위 확률
margin      1위와 2위 확률 차이
message     사용자 안내 문구
```

이 함수는 Streamlit에 의존하지 않으므로 경계값을 deterministic unit test로 검증할 수 있다.

## 데이터 흐름

```text
WAV 업로드
→ 임시 WAV 저장
→ extract_features: (1, 57)
→ scaler.transform
→ RandomForest.predict_proba
→ Top-3 정렬
→ assess_confidence
→ 결과 카드와 멜스펙트로그램 표시
→ 임시 WAV 삭제
```

## 오류 처리

- 모델 파일 누락: 기존 `FileNotFoundError` 안내와 `st.stop()` 유지
- 잘못된 WAV·feature 추출 실패: 사용자에게 예측 실패 이유 표시
- 시각화 실패: 전체 trace 대신 이해 가능한 오류 문구 표시
- 임시 WAV: 성공·실패와 관계없이 `finally`에서 삭제
- Top-3가 2개 미만인 비정상 결과: 신뢰도 판단 함수에서 명시적 `ValueError`

## 검증 계획

### 자동 검증

`assess_confidence`에 대해 다음 경계를 검증한다.

- `0.70 / 0.40` → 높음
- `0.50 / 0.35` → 높음 경계
- `0.42 / 0.30` → 보통
- `0.30 / 0.22` → 보통 경계
- `0.14 / 0.13` → 낮음
- Top-3 원소 부족 → `ValueError`

기존 pipeline에 대해서는 다음 계약을 유지한다.

- `extract_features(wav).shape == (1, 57)`
- Top-3 확률은 내림차순
- 모든 확률은 `[0, 1]` 범위

### 수동 검증

- Streamlit 앱 시작
- NewJeans WAV 업로드
- `REGGAE 14% / POP 13%`와 유사한 경우 낮은 신뢰도 표시 확인
- sidebar 10개 장르와 사용자 수정 caption 유지 확인
- 멜스펙트로그램 표시 확인
- 업로드 후 임시파일이 정리되는지 확인

## 알려진 한계

- RandomForest 확률은 calibration된 실제 정답 확률이 아니다.
- 신뢰도 threshold는 현재 평가 데이터로 최적화된 값이 아니다.
- 모델은 GTZAN 10개 장르 밖의 입력을 `unknown`으로 직접 분류하지 못한다.
- 첫 3초만 분석하므로 도입부가 곡 전체를 대표하지 않을 수 있다.
- UI 개선은 모델 정확도 향상을 의미하지 않는다.

## 포트폴리오 설명 포인트

`데이터가 부족한 상황에서 모델을 과도하게 확장하지 않고, Top-1 확률과 후보 간 margin을 이용한 상대적 신뢰도 UI를 추가했습니다. 이 값이 calibration된 확률이 아니라 heuristic임을 명시하고, 지원 장르와 OOD 한계를 화면에 노출해 모델 결과를 정답처럼 과장하지 않았습니다.`
